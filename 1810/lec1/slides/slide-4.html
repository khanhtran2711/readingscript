Slide 4

Clickstream collection and web scraping

Teaching cue: 14 to 20. The original slide says “Web Scrapping”; pronounce and explain the correct term, “web scraping”. Give pairs two minutes to classify the three project questions below.

This slide lists clickstream collection and web scraping. The wording “using software” for one and “using a programming language” for the other can be misleading. Both approaches can use software and code. The useful distinction is what we are collecting and what question it can answer.

With clickstream collection, we record instrumented activity: a product view, a basket update, or a successful registration. With web scraping, a program retrieves a page and extracts information from its content, such as product names and displayed prices. We can also obtain some published information through an available API. An API is an interface through which software requests or exchanges data in a defined format.

Consider UniCart. If we want to know how many observed sessions included “Add to basket,” we need the relevant event records. If we want to compare the price of a headphone model across several shops, published product content or an authorised product feed may help.

Scraping a competitor’s product page does not reveal every customer who clicked its checkout button. That behaviour is generally outside what the public page exposes. If a third-party service provides estimated audience behaviour, we would need to understand its source, sample, and limitations before using it.

Now classify these questions with your partner. First, which headphones are listed below 700,000 Vietnamese dong? Second, how often do observed visitors open our delivery information before checkout? Third, does our price appear higher than other shops, and do our visitors leave after checking delivery costs?

Teaching cue: Answers are published product data for the first question, instrumented events for the second, and a combination for the third. Ask one pair to explain why one source alone would be insufficient for the third question.

The combined question is common in projects. We might join product information to our own event data using a consistent product identifier. That join lets us compare observed behaviour across products with different prices. We would still need a suitable research design before claiming that a price difference caused a visitor to leave.

There is also a collection method that the slide does not list: server logs and events from the application backend. A web server can record requests and responses. The application can record that an order was accepted. Browser tracking can observe interface activity that produces no server request. Each source gives a different view of the system.

The visual on the right suggests that records can connect in complicated ways. Without a readable legend and field definitions, we should not assign a specific business meaning to its colours or lines. In a real analysis, the diagram needs a clear explanation of what each mark represents.

Transition to slide 5: We will focus now on recorded behaviour. Before discussing the collection code, we need to distinguish the individual records from the numbers calculated from them.
