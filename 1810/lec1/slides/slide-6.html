Slide 6

How the website records events

Teaching cue: 30 to 42. Reserve 3 minutes 30 seconds for the event-design task and discussion. Spend a further minute slowly tracing the collection sequence on the board. Use the remaining time for the spoken explanation.

The slide introduces a JavaScript tracker. JavaScript is code that runs in the browser and can respond to activity on a page. A tracker uses configured rules and application signals to create records and send them to an analytics collection service.

Let’s follow one basket addition. A visitor selects product H24 and presses the button. UniCart’s application updates the basket. At the agreed success point, the tracking implementation creates an add_to_cart event with the relevant product information. The browser sends a request to the collection service. That service processes the record, and reporting tools can then use it. [4, 6]

The trigger is the condition that tells our implementation when to create the event. The event name tells us what occurrence it represents. Parameters provide the details. If any of those are vague, two developers might implement the same request differently.

For example, “track the basket button” leaves an important question unanswered. Should the event mean the visitor pressed the button, or that the basket actually changed? Imagine the visitor presses it but the application returns an error. Those are different outcomes. For our UniCart measurement plan, add_to_cart will mean that the basket update succeeded. If we also need attempts, we will specify a separate event with a distinct meaning.

There is an overstatement on the slide: installing a tracker does not mean that every event will be captured. In GA4, some events are collected automatically. Enhanced measurement can collect additional supported interactions when enabled. Recommended events have standard names and parameters, but the relevant implementation is still needed. Custom events cover requirements that are not already represented suitably. [4]

Let’s apply that to the slide’s examples. Enhanced measurement can record supported file-link clicks, and it can measure video interactions for supported embedded YouTube players with the necessary API support. It does not automatically understand every video player. Its usual scroll event records the first time 90 percent of a page becomes visible. It does not give us a complete continuous trace of reading. [5]

A file_download event also needs careful interpretation. It can indicate a click on a qualifying file link. That observation alone does not prove that the file finished downloading or that the person opened and read it. A useful event name still needs its trigger definition beside it.

Registration and purchases are particularly important. For a successful registration, we could use sign_up and trigger it when the application confirms success. For an ecommerce purchase, the implementation needs to send purchase with the relevant transaction and item information. A click on “Pay now” can occur before a payment succeeds, so it is a poor definition of a completed order. [4, 6]

Now work in pairs. UniCart wants to understand successful registrations and failed checkouts. Choose one of those outcomes. Write a proposed event name, the exact trigger, two useful parameters, and one test that would tell you whether the implementation works. You have two minutes.

Teaching cue: Use the remaining 90 seconds for answers. A registration answer could use sign_up after account creation, with method and a non-sensitive registration route. A checkout-error answer could use a clearly documented custom checkout_error event when a defined failure occurs, with error_code and checkout_step. Never request the password, payment card data, or typed personal details.

If your event is checkout_error, a good test includes a known failure. You should be able to cause that test failure safely and observe the expected event once. Then complete the same step successfully and check that the error event does not appear. Testing the absence of an event can be as useful as testing its presence.

The browser is one place to collect events. A backend can also report an order confirmation because the application knows whether it accepted the order. Server-side tagging adds a server stage to how measurement data is handled. These approaches require their own design. They do not automatically recover every missing browser interaction or give permission to ignore a user’s choices. [22, 27]

Privacy affects the design from the beginning. For our exercise, record the event and the necessary operational details. Google’s policies prohibit sending prohibited personally identifiable information to ordinary Analytics collection. Avoid names, email addresses, passwords, and personal details hidden inside URLs or form values. A product identifier is enough to answer many product questions. [8, 23]

Consent mode controls how Google tags behave in response to consent choices. It does not itself obtain the choice or provide a banner. Basic and advanced implementations behave differently, so “consent denied” should not be casually translated into “every implementation sends nothing.” The project must choose and test the behaviour that matches its requirements. [7]

In a real project, the analyst’s measurement plan becomes a shared agreement with developers and the people responsible for data governance. That agreement says what an event means, when it should occur, and what data it may contain. It gives us something concrete to test after the next website update.
