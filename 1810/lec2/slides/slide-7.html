Slide 7

Interpreting an event report

Teaching cue: 25 to 30. Point to Event name, Count, Users, and the two change columns. Allow 45 seconds to calculate add_to_cart events per listed user, then discuss one possible explanation.

This screenshot is an earlier GA4 event-management view. Its “Mark as conversion” label is historical. In current standard GA4 reporting, we use the key-event terminology for important business actions. Changing that label does not alter our responsibility to define the action correctly. [5]

Start with the add_to_cart row. The report shows 22,872 events and 6,357 users. The count tells us how often the recorded event occurred. The user column tells us how many users triggered it under that report’s definition. Dividing those values gives approximately 3.60 basket-addition events per listed user who added something.

What could explain that? A person may add several products, change quantities, or return on another visit. A duplicate tracking implementation could also increase the count. The ratio tells us that events and users differ. It does not identify the reason on its own.

Look at the percentage-change columns. Basket additions increased by 24.7 percent while the listed user count increased by 15.4 percent. This suggests the event count grew faster than the number of users who triggered it. Before celebrating, check that the comparison periods have the same length and that the tracking definition remained consistent.

The general calculation is the new value minus the previous value, divided by the previous value, multiplied by one hundred. If the previous value is zero, that ordinary percentage-change formula is undefined. Report the absolute change and explain the starting point instead.

At the bottom, data_import_success fell by 85.7 percent to one event. That is a large relative change from a small count. A value around seven in the earlier period would produce that result. We should ask the implementation owner how often this technical event was expected. It does not automatically mean customer activity collapsed.

We also cannot read this table as a completed funnel. The rows show aggregate events across the selected period. They do not establish that the same sessions performed each action in order. To estimate checkout completion, define a cohort and follow its ordered steps using consistent session or user rules.

In a project meeting, a useful finding would be: “Basket-addition activity increased. We should check the event implementation and compare confirmed purchases before deciding whether the increase represents business improvement.” That sentence connects the observation to a proportionate investigation.
